发现

端到端实跑暴露的三件事（均未修，各自独立评估）

一｜循环依赖误报：函数内延迟导入被算成图边

评审报出 _compat/v2.py → params.py → datastructures.py → _compat/v2.py 的环， 但逐边核对后：3 条边有 2 条是函数作用域的延迟导入（v2.py:350、 datastructures.py:148），只有 params.py:16 是顶层导入。 导入期不存在这个环 —— 作者正是用延迟导入打破它的。 而报告「依赖关系」一节反而正确地把同一处延迟导入描述为「主动规避循环依赖的例证」， 两处口径互相矛盾：模块子 Agent 读了源码看出是规避手段，评审只看图。 依赖图不区分「导入期依赖」与「调用期依赖」，这是一类可复现的误报。 影响 U4 的图、U6 的深挖列表、U11 的结构类检查，改动面大，故未动。

二｜「完整分析」与「U9 仍抽样」不可兼得（与 D3 口径有出入）

real_nodes.py:218 传给 build_index 的是 [f.path for f in outcome.parsed] —— 全量 parsed 文件，代码里没有抽样开关。所以你授权的一次完整分析必然连带做全量索引。 本次实际 1138 个可解析文件 → 6529 个切块 / 105 批 embedding。 上次基准记录的「只索引前 60 个文件」是当次跑法的限制，不是代码行为。 正面副作用：U9「抽样导致部分查询找不到」那条限制随之解除，检索质量现在可被真实评估。

三｜三条分支不是真并行，索引占了 83% 的墙钟时间

builder.py 的注释图把 Planner / Reviewer / 索引画成三路并行，但 LangGraph 的 superstep 语义下 planner、select_files、chunk_and_index 同属一个 superstep， 下一个 superstep（模块扇出、Reviewer）必须等整个当前 superstep 结束才启动。 实测：总跨度 36.6 分钟，其中索引段 30.5 分钟（105 批 embedding）， 扇出+评审+汇总只用 5.3 分钟（45 次 chat）。索引跑完前 chat 调用一直停在 2 次。 即用户提交后要等 30 分钟才开始有模块分析；若三者真并行，总耗时应约 30.5 分钟而非 36.6。 这条影响「首次分析要等多久」这个用户可感知的量，值得单独评估是否要改。
